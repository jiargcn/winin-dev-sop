# ENG-04：配置、构建和 GitHub Actions 调整

## 1. 适用条件、反例和选择规则

本流程适用于应用配置、构建脚本、Maven/npm 任务、GitHub Actions、环境参数或制品生成方式调整。配置实际改变业务规则时应使用 `REQ-02`；依赖版本升级使用 `ENG-02`。

局部开发配置为 `L1`；影响共享构建、生产配置、密钥、制品、发布兼容或多个仓库时为 `L2/L3`，并按需叠加 `SECURITY`、`COMPATIBILITY` 或 `CROSS-MODULE`。

## 2. 必要输入、缺失处理和开始条件

取得变更目标、当前配置来源、覆盖优先级、适用环境、调用者、密钥管理方式、当前流水线和回退版本。敏感值只确认引用和权限，不读取或复制明文。

## 3. 任务澄清、验收标准和范围

明确哪些环境和分支生效、配置缺失或非法时的行为、制品是否变化、缓存和权限影响。验收必须覆盖干净环境可重复构建、错误配置可诊断以及不受影响环境保持正常。

## 4. 项目与代码上下文准备

收集 `pom.xml`、前端脚本、GitHub Actions 工作流、配置模板、环境变量说明和现有构建日志。建立配置从定义、默认值、覆盖到运行读取的链路，确认仓库已有用户改动并避免覆盖。

## 5. 现状、影响和证据分析

分析配置来源和优先级、触发条件、权限、缓存键、制品路径、矩阵构建和失败处理。对比本地与 GitHub Actions 环境，识别仅在开发机存在的隐式依赖。检查是否影响其他分支、仓库或复用工作流。

## 6. 开发方案设计

方案说明目标行为、配置 schema 或工作流变化、默认值、校验、敏感信息引用、兼容、失败提示和回退。高风险配置采用先校验后启用，避免缺失时静默使用不安全默认值。

## 7. 专用测试用例设计

至少覆盖：

- 默认、合法、缺失、非法和旧版配置。
- 分支、事件、矩阵和缓存命中/失效。
- 干净环境、重复执行、失败重试和取消。
- 最小权限、密钥不可见和日志脱敏。
- 制品内容、版本、校验和与可重复构建。
- 回退到上一配置或工作流版本。

## 8. 分步编码与每轮验证

先修改并验证最小配置或工作流单元，再在分支上触发 GitHub Actions。每次只改变一个主要行为，避免同时重写多个流水线。不得为测试方便把密钥改成明文或扩大令牌权限。

## 9. AI 差异审查、人工检查和风险复核

让 AI 检查 YAML 条件、权限、触发范围、缓存、环境变量、命令注入和失败处理。开发人员核对实际运行日志、制品和权限；AI 对 CI 语法的判断不能替代真实流水线执行。

## 10. 自测、结果记录和完成条件

本地执行受影响的 Maven/npm 命令，在 GitHub 分支上运行相关 Actions，检查成功、预期失败和制品。记录运行链接、环境摘要、结果、权限和回退验证。所有必需门禁恢复可用后才能完成。

## 11. 必须保留的最终产物

- 配置或流水线目标、影响范围和方案。
- 配置、脚本、工作流及相应测试变更。
- GitHub Actions 运行结果和制品验证。
- 权限、兼容、回退和剩余风险。

## 12. 停止、升级或评审条件

需要读取明文密钥、扩大仓库/云资源权限、影响保护分支或无法安全试运行时停止并升级。生产配置与仓库配置来源冲突时先确认权威来源。

## 13. 禁止事项

禁止提交密钥；禁止使用过宽令牌权限；禁止以跳过测试使流水线通过；禁止只验证 YAML 可解析；禁止覆盖不相关工作流；禁止让缓存掩盖依赖或构建错误。
