# REQ-02：现有功能业务规则、流程、状态或行为变更

## 1. 适用条件、反例和选择规则

本流程适用于改变已存在功能的业务规则、流程顺序、状态转换、计算口径或可观察行为。新增可独立验收的能力使用 `REQ-01`；仅改善交互且业务结果不变使用 `REQ-03`；修复违反现有规则的行为使用对应缺陷流程。

默认风险等级为 `L2`。改变关键 MOM 状态、数据库结构、公共契约、权限或跨系统事实时为 `L3`。

## 2. 必要输入、缺失处理和开始条件

必须取得变更前规则、目标规则、生效对象、适用版本、历史数据处理口径、兼容要求和验收标准。代码、任务描述、用户口述与实际运行行为不一致时，先确定哪一项是权威现状；不得让 AI 静默选择。

## 3. 任务澄清、验收标准和范围

使用“当前行为—目标行为—差异—不变项”结构澄清任务。明确新规则从何时生效，是否影响在途单据、历史数据、旧客户端、外部系统和报表。验收必须同时证明目标行为成立以及声明不变的行为没有被破坏。

## 4. 项目与代码上下文准备

固定 Git 基线并运行现有测试。沿页面或接口入口追踪到领域服务、状态机、数据写入、事件、查询投影和下游调用方。跨模块、陌生代码库或文档不足时刷新 Understand Anything 图谱；局部规则变更采用定向调用链和历史提交分析。

获取最新 PostgreSQL DDL、配置、接口契约和代表性历史数据结构。生产数据进入 AI 前必须遵循项目规则并完成最小化脱敏。

## 5. 现状、影响和证据分析

为当前规则建立可执行证据：现有测试、代码条件、数据库约束、配置或实际样例。列出所有读写该状态或字段的入口、定时任务、消息消费者、统计查询和外部调用方，避免只修改最明显的页面或接口。

命中 `MOM-DOMAIN` 时核对业务对象、状态不变量和事实所有权，特别区分申请、任务、执行记录与结果，以及库存预期、事务与余额。

## 6. 开发方案设计

方案说明规则变化点、状态迁移、数据与接口影响、兼容策略、在途对象处理、异常恢复、回退和可观测性。若新旧规则需并存，明确选择条件、有效期、默认值及移除旧逻辑的后续条件。

不得仅以增加条件分支作为方案；需要解释业务不变量如何保持。`L3` 方案必须在编码前人工评审。

## 7. 专用测试用例设计

测试至少覆盖新旧规则差异表中的每一行，并增加：

- 变更前合法数据在新版本中的行为。
- 临界时间、状态边界、空值、极值和重复操作。
- 非法状态跳转、撤销、冲销、返工和补偿。
- 并发更新、幂等和事务失败。
- 旧客户端、旧接口调用方和历史数据兼容。
- 明确声明不变的相关功能回归。

测试薄弱项目先补当前行为的特征测试，再改变实现并更新目标断言。

## 8. 分步编码与每轮验证

先固化旧行为基线，再按最小差异修改领域规则，随后处理数据库、接口和前端表现。每一步运行相关 JUnit 5/Mockito 或 Vitest 测试，并检查是否出现双重规则、绕过入口或无效旧分支。

## 9. AI 差异审查、人工检查和风险复核

要求 AI 对照当前与目标行为表审查最终差异，重点寻找遗漏入口、状态穿透、兼容破坏、重复执行和测试缺口。开发人员核对所有调用方、配置和数据库约束，并确认没有扩大需求范围。

## 10. 自测、结果记录和完成条件

执行 `mvn test`、适用的 `mvn verify`、`npm run test` 和 `npm run build`。使用新数据、历史数据、在途状态和异常路径完成自测，确认 GitHub Actions 通过。自测报告必须同时记录新行为证据和旧行为回归证据。

## 11. 必须保留的最终产物

- 当前与目标行为差异及开发方案。
- 评审结论、代码与测试变更。
- 历史数据和兼容性处理结论。
- 自测报告、Pull Request 摘要和剩余风险。

## 12. 停止、升级或评审条件

无法确认现行规则、历史数据口径、状态所有权或在途对象处理时停止。发现公共契约、DDL、关键业务事实或权限变化时升级为 `L3`。

## 13. 禁止事项

禁止把当前代码行为自动视为正确业务规则；禁止只测试新路径而不回归旧路径；禁止用默认值掩盖兼容决策；禁止删除旧逻辑但遗漏历史数据、在途单据或外部调用方。
