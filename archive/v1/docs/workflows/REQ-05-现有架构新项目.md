# REQ-05：基于公司现有架构建设全新项目

## 1. 适用条件、反例和选择规则

本流程适用于新建项目，但技术架构、工程骨架、开发规范和主要组件均复用公司已批准基线。需要评估或引入全新架构使用 `REQ-06`；在已有项目中增加模块使用 `REQ-01`。

新项目默认至少为 `L2`。包含公共平台能力、核心数据模型、跨系统集成或安全边界时为 `L3`。

## 2. 必要输入、缺失处理和开始条件

必须取得项目目标、用户与场景、范围边界、里程碑、部署约束、复用的架构基线及版本、业务域、相邻系统、数据来源和非功能目标。未验证的客户需求、业务量和集成能力应作为假设，不得写成已确认事实。

## 3. 任务澄清、验收标准和范围

定义最小可交付业务闭环，而不是直接罗列页面。明确首期范围、范围外、相邻系统、角色、业务结果和可观察验收；对未来能力只保留演进边界，不提前实现。

## 4. 项目与代码上下文准备

取得公司标准项目骨架、参考项目、架构决策、依赖清单、GitHub Actions、编码规范和测试范例。对参考项目使用 Understand Anything 建立最新知识图谱，确认哪些属于通用架构、哪些只是特定项目实现，避免复制客户规则和历史缺陷。

准备 Java 17、Spring Boot 3、Maven、Vue 3、Vitest 和 PostgreSQL 的受控版本基线，确认第三方依赖来源与许可证要求。

## 5. 现状、影响和证据分析

现状分析对象是公司架构基线和参考项目，而不是不存在的新系统。建立“直接复用、需配置、需扩展、明确不复用”矩阵，检查架构基线对当前业务量、安全、集成和部署约束是否仍适用。

## 6. 开发方案设计

方案先描述业务闭环、领域边界、事实所有权、模块职责和外部协作，再展开应用结构、数据、接口、权限、异常、一致性、可观测性和测试策略。MOM 项目必须明确 MES、WMS、QMS、EAM 等领域权威事实，避免以统一数据库代替边界设计。

为首期范围建立可演进但不过度设计的模块边界。`L3` 的总体方案和关键接口在主体开发前人工评审。

## 7. 专用测试用例设计

测试体系至少包括：

- 领域规则和状态不变量的 JUnit 5 单元测试。
- 数据访问、事务和 PostgreSQL 约束的集成测试。
- API 契约、权限、幂等和异常响应测试。
- Vue 组件、状态和关键操作的 Vitest。
- 关键业务闭环、跨系统失败补偿和追溯验收。
- 构建、静态检查和 GitHub Actions 门禁。

## 8. 分步编码与每轮验证

先建立最小可构建骨架和流水线，再按可独立验收的业务纵切片交付。每个切片包含必要的后端、前端、数据、权限和测试，不长期保留只有表或只有页面的半成品链路。

## 9. AI 差异审查、人工检查和风险复核

AI 审查重点检查对参考项目的错误复制、架构基线偏离、领域边界混乱、依赖风险、测试空洞和过度设计。开发人员必须核对生成的配置、依赖版本、许可证、默认口令和安全设置。

## 10. 自测、结果记录和完成条件

每个切片执行 Maven 与 npm 测试和构建，验证数据库初始化、关键接口、权限和业务闭环。GitHub Actions 必须能在干净环境重复构建。项目骨架、启动说明和首个业务闭环均通过后，相关任务才可交付。

## 11. 必须保留的最终产物

- 项目开发方案、架构复用矩阵和评审结论。
- 可重复构建的代码、数据库迁移、测试和 GitHub Actions。
- 关键业务闭环自测报告。
- 架构偏差、假设、限制和后续演进条件。

## 12. 停止、升级或评审条件

公司架构基线不满足关键约束、参考项目规则无法区分、核心事实所有权未决或需要新增平台级组件时停止并升级评审。若主要架构已不再复用，应切换到 `REQ-06`。

## 13. 禁止事项

禁止复制参考项目中的客户数据、密钥和私有规则；禁止把项目骨架搭建等同于业务完成；禁止在没有业务闭环时先建设大量通用组件；禁止绕过依赖、安全和构建基线。
