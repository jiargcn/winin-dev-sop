# ENG-01：代码重构与技术债治理

## 1. 适用条件、反例和选择规则

本流程适用于改善结构、可读性、重复、复杂度或可测试性，同时保持外部可观察行为、公共契约、业务状态和数据语义不变。只要业务结果或规则改变，就应使用对应需求流程；性能目标为主时使用 `REQ-04`。

局部重构通常为 `L1`，跨模块、公共基础组件或测试基础薄弱时为 `L2`；触及公共契约、关键数据或安全边界时不再是普通重构，按 `L3` 处理。

## 2. 必要输入、缺失处理和开始条件

取得技术债问题、影响证据、重构目标、明确不变项、代码基线和回归范围。不能说明重构带来的维护收益或无法定义行为不变时，不应开始大范围修改。

## 3. 任务澄清、验收标准和范围

把目标写成可验证指标，例如减少重复、降低复杂依赖、建立测试接缝或消除循环引用。明确哪些模块、接口、数据库行为、异常和日志语义保持不变。验收同时检查结构改善和行为等价。

## 4. 项目与代码上下文准备

运行现有测试与构建，建立基线失败清单。跨模块重构或依赖关系不清时使用 Understand Anything/依赖检索建立图谱；局部方法重构使用定向调用方和测试分析。收集公共 API、序列化格式、配置和反射使用点。

## 5. 现状、影响和证据分析

识别需要改善的结构问题及其实际影响，列出所有调用方、扩展点、测试、配置和运行时绑定。对于自动化测试薄弱区域，先通过特征测试固定当前正确行为，避免把潜在业务规则误当成坏代码删除。

## 6. 开发方案设计

方案应描述目标结构、迁移顺序、行为不变量、兼容方式、每步回退和完成判据。大范围重构拆成能够单独构建和验证的小步骤，必要时先增加适配层再迁移调用方。

## 7. 专用测试用例设计

测试以行为等价为核心，覆盖公共入口、边界、异常、序列化、事务、权限和关键 MOM 状态。增加特征测试、契约测试或快照式结果对比，但快照必须可解释，不能保存无意义的大块输出。

## 8. 分步编码与每轮验证

遵循“补测试—移动或抽取—切换调用方—删除旧实现”的顺序。每次只改变一种结构并运行最近层级测试。使用自动重构工具后仍需人工检查语义和运行时引用。

## 9. AI 差异审查、人工检查和风险复核

要求 AI 查找意外行为变化、遗漏调用方、反射/配置引用、异常语义变化和过度抽象。开发人员比较重构前后公共行为，并确认没有把旧缺陷或业务特例在无证据情况下“清理”。

## 10. 自测、结果记录和完成条件

执行相关 `mvn test`、`mvn verify`、`npm run test`、`npm run build` 和 GitHub Actions。对关键入口做前后结果对比，确认结构目标已达到且行为不变。覆盖不足部分必须记录人工验证步骤。

## 11. 必须保留的最终产物

- 重构目标、行为不变量和影响范围。
- 特征测试、重构代码和回归测试。
- 自测报告与 Pull Request 结构变化摘要。
- 未迁移区域和剩余技术债。

## 12. 停止、升级或评审条件

发现必须改变业务行为、公共契约、数据库语义或权限边界时停止并重新分类。缺少足够测试且无法建立特征基线时缩小范围或先建测试。

## 13. 禁止事项

禁止以重构名义改变规则；禁止一次性全量重写；禁止为了测试通过删除业务特例；禁止引入没有消费者的抽象；禁止在大范围格式化中隐藏实质变更。
