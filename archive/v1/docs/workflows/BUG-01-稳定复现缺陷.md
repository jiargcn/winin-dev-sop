# BUG-01：可稳定复现的功能缺陷

## 1. 适用条件、反例和选择规则

本流程适用于相同步骤、数据和环境下能够稳定出现，且实际行为违反已确认规则、验收标准或历史正确行为的缺陷。依赖特定环境差异使用 `BUG-02`；不能稳定复现但有现场证据使用 `BUG-03`；主要表现为数据不一致、性能或安全问题时分别使用 `BUG-05`、`BUG-06` 或 `BUG-07`。

局部且可逆的修复通常为 `L1`；影响业务状态、数据库、接口、权限或多个模块时升级到 `L2/L3`。

## 2. 必要输入、缺失处理和开始条件

取得问题版本、环境、角色、前置数据、操作步骤、期望结果、实际结果和稳定复现证据。任务描述中的“应该”必须能追溯到需求、业务规则或提出人确认。无法确认期望行为时先澄清，不得把当前代码与 AI 判断的差异直接认定为缺陷。

## 3. 任务澄清、验收标准和范围

将复现步骤压缩为最小案例，明确问题首次出现版本、影响范围和不受影响场景。验收标准至少包括原问题不再发生、回归测试修复前失败修复后通过、相邻正确行为保持不变。

## 4. 项目与代码上下文准备

固定缺陷版本与修复基线，运行现有构建和相关测试。范围明确时使用定向代码检索、断点、调用链和历史提交分析，无需机械构建全量图谱；跨模块或陌生代码库时刷新 Understand Anything 图谱。

准备与问题一致的配置、DDL 和最小脱敏数据。不得在不一致环境中复现后直接归因于代码。

## 5. 现状、影响和证据分析

先复现并保存输入、实际输出、日志或失败测试，然后沿数据和调用链定位第一个偏离预期的位置。建立“现象—直接原因—根因—为何现有测试未发现”的因果链，区分触发条件与根因。

检查同一错误模式是否存在于其他入口，但扩展修复范围前评估风险并记录依据。

## 6. 开发方案设计

选择能够消除根因的最小修复，说明变更位置、保持不变的行为、异常处理、兼容与回退。若只能缓解现象而未确认根因，应明确标为临时措施，并附后续诊断条件。命中高风险标签时形成正式方案并评审。

## 7. 专用测试用例设计

优先将最小复现转换为自动化回归测试，保证修复前失败、修复后通过。补充根因边界、相邻正确行为、异常输入、重复操作、权限和历史数据用例。无法自动化时保存可重复步骤、数据准备和可观察结果。

## 8. 分步编码与每轮验证

先提交失败测试或保存失败证据，再实施最小修复并运行最近层级测试。随后执行相邻模块回归。不得通过删除失败测试、扩大容错或吞掉异常使测试表面通过。

## 9. AI 差异审查、人工检查和风险复核

让 AI 根据复现证据、根因、方案和最终差异检查是否只修复症状、是否引入宽泛条件、异常吞噬、空值或兼容问题。开发人员逐文件检查，并验证建议不会改变已确认业务规则。

## 10. 自测、结果记录和完成条件

执行缺陷回归测试、相关 `mvn test`、适用的 `mvn verify`、前端 `npm run test` 和 `npm run build`。按原始复现步骤再次验证，确认 GitHub Actions 通过。记录修复前后证据和相邻回归结果。

## 11. 必须保留的最终产物

- 最小复现证据、根因结论和修复方案。
- 修复代码及回归测试。
- 自测报告与 Pull Request 摘要。
- 临时措施、未验证项和剩余风险。

## 12. 停止、升级或评审条件

无法确认期望行为、无法复现却又没有现场证据、根因指向数据库/接口/权限/关键业务状态时停止或升级。修复范围明显超过原任务时重新分级。

## 13. 禁止事项

禁止未复现先改代码；禁止把异常捕获后忽略；禁止删除或放宽正确断言；禁止只凭相关性认定根因；禁止在修复缺陷时顺带重构无关代码。
