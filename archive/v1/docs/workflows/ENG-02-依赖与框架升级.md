# ENG-02：依赖、框架和基础组件升级

## 1. 适用条件、反例和选择规则

本流程适用于升级或替换 JDK、Spring Boot、Maven 依赖、Node、Vue 生态组件、数据库驱动或基础库。只修复业务代码缺陷使用对应缺陷流程；因升级而必须适配外部接口时可叠加 `CONTRACT`。

补丁级局部依赖通常为 `L1/L2`；JDK、Spring Boot、Vue 主版本、数据库驱动、安全组件或多个服务共同升级时为 `L3`，并叠加 `COMPATIBILITY`，安全修复还叠加 `SECURITY`。

## 2. 必要输入、缺失处理和开始条件

取得升级原因、当前与目标版本、官方发布说明、支持周期、已知不兼容项、许可证、受影响项目和回退版本。版本信息必须来自当前官方资料或受控制品库，不依据 AI 记忆选择“最新版本”。

## 3. 任务澄清、验收标准和范围

明确本次只升级哪些组件、是否允许传递依赖变化、目标运行环境和兼容范围。验收应覆盖构建、测试、运行、配置、性能、安全扫描和关键业务回归。

## 4. 项目与代码上下文准备

保存依赖树、锁定文件、构建插件、JDK/Node 版本、容器镜像和 GitHub Actions 基线。使用依赖分析和代码检索确认被废弃 API、自动配置、序列化、反射和插件影响；跨项目时建立升级矩阵。

## 5. 现状、影响和证据分析

比较官方迁移指南和项目实际用法，区分直接依赖、传递依赖和仅测试依赖。检查 Spring Boot 自动配置、Jakarta 命名空间、数据库驱动行为、Vue 组件 API、构建插件与 Node 兼容。安全升级需确认漏洞可达性和修复版本。

## 6. 开发方案设计

优先采用逐层升级和可回退版本，说明依赖约束、代码适配、配置迁移、数据或协议兼容、灰度和回退。主版本升级应拆分基础构建、编译适配、测试修复和行为回归，不把所有变化混在一次不可解释提交中。

## 7. 专用测试用例设计

至少覆盖：

- 干净环境依赖解析、编译、打包和启动。
- 关键自动配置、序列化、数据库访问和事务。
- 公共 API、消息、文件及历史数据兼容。
- 核心业务回归、权限和异常处理。
- 前端组件、浏览器构建和静态资源。
- 升级、降级和回退演练。

## 8. 分步编码与每轮验证

先更新运行时和构建基线，再逐个依赖组升级，处理编译问题后运行行为测试。锁定最终依赖版本，检查没有意外降级、重复版本或未知仓库来源。每个阶段保持可构建。

## 9. AI 差异审查、人工检查和风险复核

AI 可辅助归纳迁移说明和扫描废弃 API，但开发人员必须核验官方来源。审查最终依赖树、许可证、默认配置变化、安全设置、传递依赖和被跳过测试，不自动接受批量版本更新。

## 10. 自测、结果记录和完成条件

执行 `mvn dependency:tree`、`mvn test`、`mvn verify`、`npm install` 或项目锁定安装方式、`npm run test`、`npm run build`，并验证干净 GitHub Actions。完成启动、数据库、关键业务和回退检查。

## 11. 必须保留的最终产物

- 当前/目标版本、升级原因和官方依据。
- 兼容矩阵、迁移方案和评审结论。
- 依赖、代码、配置与测试变更。
- 自测、依赖树、安全/许可证结果和回退说明。

## 12. 停止、升级或评审条件

目标版本不受公司运行环境支持、许可证不明、关键插件不兼容、无法回退或测试不足以判断行为变化时停止。发现主版本或安全边界变化时升级 `L3`。

## 13. 禁止事项

禁止直接采用 AI 声称的最新版本；禁止忽略锁定文件和传递依赖；禁止为了编译通过关闭安全或测试插件；禁止把大量依赖升级与业务功能混在同一变更；禁止未验证就删除兼容配置。
