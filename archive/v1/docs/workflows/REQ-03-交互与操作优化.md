# REQ-03：现有功能易用性、操作效率或交互优化

## 1. 适用条件、反例和选择规则

本流程适用于业务结果原则上不变，但需要减少操作步骤、改善反馈、优化页面布局或提高现场操作效率的任务。业务规则、状态或结果变化使用 `REQ-02`；响应时间和吞吐量目标使用 `REQ-04`；错误行为修复使用缺陷流程。

局部纯前端调整通常为 `L1`；影响后端接口、权限、状态、PDA/现场端或多个角色时为 `L2`，命中高风险标签时为 `L3`。

## 2. 必要输入、缺失处理和开始条件

取得当前页面或操作路径、目标用户、使用设备、问题证据、期望改善、保持不变的业务规则和可观察验收标准。只有“看起来不好用”而没有具体场景时，应向提出人确认高频任务、主要阻碍和成功标准。

## 3. 任务澄清、验收标准和范围

记录优化前后的操作步骤、信息呈现、反馈时机和错误恢复方式。明确桌面、PDA、线边端的适用范围，以及键盘、扫码、触控、多窗口和弱网等约束。终端只是业务执行入口，不得借交互优化改变所属业务域的事实规则。

## 4. 项目与代码上下文准备

确认 Vue 3 组件、路由、状态管理、API、权限指令、样式体系和现有 Vitest 测试。检查后端接口是否已经支持目标交互；涉及多个组件或陌生前端架构时使用知识图谱或定向依赖分析。运行现有前端测试与构建，记录基线异常。

## 5. 现状、影响和证据分析

以实际用户任务为单位分析，而不是只看单个组件。确认加载、空态、错误态、权限态、重复提交、刷新、返回和并发操作的当前行为。列出共享组件、多个入口和不同分辨率的影响，区分用户问题证据与设计偏好。

## 6. 开发方案设计

方案应包含优化前后操作流、信息层级、组件变化、状态与错误反馈、无障碍或键盘操作、接口依赖和回退方式。若需要改变后端数据或业务状态，应重新选择 `REQ-02` 或升级风险等级，而不是隐藏在前端方案中。

## 7. 专用测试用例设计

至少覆盖：

- 主任务的完整操作链和步骤减少结果。
- 初始加载、空数据、慢响应、接口错误和重试。
- 重复点击、快速切换、刷新、返回和多窗口。
- 不同角色、只读状态和无权限入口。
- 表单校验、焦点、键盘/扫码、长文本和边界数据。
- 共享组件和相邻页面回归。

对关键状态转换和工具函数补 Vitest；无法自动化的视觉或设备行为形成可重复检查清单。

## 8. 分步编码与每轮验证

先增加或修正组件测试，再按页面结构、交互状态、错误处理和样式逐步修改。每次运行相关 Vitest，并在代表性浏览器和设备尺寸检查。后端未变时不得顺手调整接口契约。

## 9. AI 差异审查、人工检查和风险复核

让 AI 对照目标操作流审查事件处理、状态同步、重复提交、权限、空值和测试缺口。开发人员实际操作关键路径，检查 AI 无法可靠判断的视觉层级、焦点、设备输入和业务可理解性。

## 10. 自测、结果记录和完成条件

执行 `npm run test` 与 `npm run build`；涉及后端时执行相关 `mvn test`。完成主要设备尺寸、角色、异常反馈和相邻页面回归，确认 GitHub Actions 通过。记录优化前后可观察差异，而不是只写“页面正常”。

## 11. 必须保留的最终产物

- 优化前后操作流或验收对照。
- Vue 代码、Vitest 测试及必要的后端变更。
- 自测报告和关键交互验证结果。
- Pull Request 摘要、限制和剩余风险。

## 12. 停止、升级或评审条件

发现业务规则、状态、权限含义或接口契约必须改变时停止并重新分类或升级。PDA/现场操作可能造成重复业务执行、漏扫或错绑时至少按 `L2` 处理并确认业务防重规则。

## 13. 禁止事项

禁止只根据 AI 或开发人员审美改变界面；禁止用隐藏按钮代替权限控制；禁止只测正常点击；禁止为减少步骤绕过确认、校验、审批或业务安全门禁。
