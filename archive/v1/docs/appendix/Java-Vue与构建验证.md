# Java 17、Spring Boot 3、Vue 3 与构建验证

## 1. 环境基线

开始任务和提交前分别确认工具版本，避免本地环境与 GitHub Actions 不一致：

```powershell
java -version
mvn -version
node --version
npm --version
```

项目的 `pom.xml`、Maven Wrapper、`package.json`、锁定文件和 GitHub Actions 是版本依据。存在 `mvnw` 时优先使用项目 Wrapper；存在 `package-lock.json` 时，干净验证优先使用 `npm ci`，日常增量开发遵循项目约定。

## 2. 后端验证顺序

后端变更至少按以下顺序验证：

1. 运行最接近变更的 JUnit 5/Mockito 测试，快速验证当前切片。
2. 运行相关模块测试；多模块影响时运行上层聚合模块测试。
3. 提交前运行项目规定的完整门禁，默认参考命令如下。

```powershell
mvn test
mvn verify
```

如果项目区分单元测试与集成测试，应执行项目 `pom.xml` 中定义的 profile 或插件目标。不得自行假设跳过测试参数是可接受的提交方式。

测试应关注业务结果和不变量，而不是只验证方法被调用。Mockito 用于隔离明确的外部依赖，不应把领域规则全部 mock 掉。数据访问、事务、序列化和 Spring 配置行为需要相应的集成验证。

## 3. 前端验证顺序

前端变更先运行相关 Vitest，再运行完整测试和生产构建：

```powershell
npm run test
npm run build
```

如果项目提供 `test:unit`、`test:coverage`、`lint` 或 `type-check` 等脚本，应按仓库说明执行。不要绕过锁定文件或在没有说明的情况下改用另一包管理器。

Vitest 测试至少验证组件状态、事件、数据转换、权限表现、重复提交和错误反馈。浏览器布局、PDA 扫码、焦点和设备交互等难以由单元测试覆盖的部分，应形成可重复人工检查步骤。

## 4. 自动化测试薄弱项目

存量项目测试不足时，按以下优先级补充：

1. 为即将修改的当前正确行为建立特征测试。
2. 为缺陷建立修复前失败、修复后通过的回归测试。
3. 为新增领域规则和纯函数建立快速单元测试。
4. 为数据访问、事务、接口契约和关键配置建立集成测试。
5. 暂时无法自动化的路径使用版本化数据和可重复操作步骤验证，并在自测报告中说明缺口。

不得要求一个普通任务一次性补齐整个项目的测试债，但必须保护本次变更涉及的关键行为。

## 5. 失败处理

区分基线已有失败和本次新增失败。开始任务时已经存在的失败应记录命令、时间和输出摘要；本次变更引入的失败必须修复。测试不稳定时先固定随机种子、时间、并发、外部依赖和数据，再判断是产品问题还是测试问题。

AI 可以分析失败日志和提出修复建议，但不得通过删除测试、放宽断言、增加无界等待或吞掉异常使构建表面通过。
