# GitHub 协作与质量门禁

## 1. 分支与工作区

开始任务前确认目标仓库、基线分支和任务分支，检查工作区已有修改。现有修改属于开发人员或其他任务时应保留并隔离，不能用覆盖、重置或大范围格式化清除。

提交应围绕单一任务目标，避免把依赖升级、无关重构和格式化混入业务修复。提交信息能够说明意图，但最终审查以完整差异和 Pull Request 为准。

## 2. 提交前个人审查

在创建 Pull Request 前完成：

1. 对照任务目标检查最终差异，确认所有修改有明确原因。
2. 检查调试代码、临时日志、注释掉的逻辑、跳过测试、生成文件和敏感信息。
3. 运行与风险范围相符的 Maven、Vitest、构建、数据库和专项测试。
4. 使用 AI 对最终差异做一次独立审查，重点检查正确性、安全、兼容、异常路径和测试缺口。
5. 开发人员逐条判断 AI 建议，只修改经过证据或测试验证的问题。

## 3. Pull Request 内容

Pull Request 应关联任务单，并使用[描述模板](../templates/Pull-Request描述模板.md)说明场景、风险、目的、实际变更、设计评审、测试、兼容、数据、回退和剩余风险。`L3` 任务必须能追溯到人工方案评审。

AI 审查结果只是辅助意见，不构成批准。经过实质修改后应重新运行相关测试并重新检查差异。

## 4. GitHub Actions

Actions 应在干净、可重复环境执行构建和测试。工作流至少覆盖项目规定的 Java/Maven 与 Vue/npm 门禁，并根据项目增加静态检查、安全、制品或数据库迁移验证。

出现失败时先区分基线问题、环境问题、测试不稳定和本次回归。不得通过修改触发条件、增加无条件跳过、忽略退出码或放宽分支规则使失败表面消失。

## 5. 敏感信息

密钥和令牌使用 GitHub 受控 Secrets 或项目批准的密钥管理方式。工作流采用最小权限，外部 Pull Request、第三方 Action 和脚本输入需防止命令注入或密钥泄露。日志和制品不得包含连接串、令牌或未脱敏客户数据。

## 6. 交付状态

Pull Request 建立和 Actions 通过只表示代码已达到开发交付门槛，不等于正式测试、上线或生产数据执行已批准。后续环节需要的环境、数据脚本、开关、观察项和回退条件必须在描述中清晰交接。
