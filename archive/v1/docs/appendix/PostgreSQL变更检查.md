# PostgreSQL 变更检查

## 1. 权威基线

涉及数据库的任务必须确认目标应用版本对应的 PostgreSQL DDL、迁移记录和目标环境 schema 版本。开发库中的临时结构、ORM 推断和 AI 生成 DDL 不能自动作为权威基线。

至少检查表、字段、类型、默认值、NULL、主外键、唯一约束、检查约束、索引、序列、视图、触发器、函数和迁移顺序。需要使用数据分布时采用只读、最小化、脱敏查询。

## 2. DDL 设计检查

- 说明新旧应用版本与 schema 的兼容窗口。
- 评估加锁类型、表规模、执行时间、磁盘、WAL 和复制影响。
- 新字段明确 NULL、默认值、历史数据填充和后续收紧约束的顺序。
- 索引基于查询和执行计划设计，评估写入成本、重复索引和创建方式。
- 约束和默认值表达业务不变量时，与应用校验保持一致。
- 删除或重命名采用扩展—迁移—切换—清理路径，不在单步中破坏旧版本。

## 3. SQL 与性能检查

使用代表性数据检查执行计划、估算行数、连接顺序、索引、排序、临时文件和锁。性能结论需记录 PostgreSQL 版本、数据规模、参数和实际执行证据，不能只依赖 AI 对 SQL 文本的判断。

批量脚本应避免一次处理不可控数据量，明确批大小、排序依据、提交策略、断点续跑和并发限制。分页或批处理排序必须稳定，防止遗漏和重复。

## 4. 数据脚本结构

一个可交付的数据变更至少包含：

1. 前置检查：确认 schema 版本、数据条件和执行前提。
2. 只读预览：输出预计影响行数和分布，不修改数据。
3. 正式脚本：具备明确筛选、事务/分批、错误处理和幂等。
4. 独立对账：不复用正式脚本的相同假设，验证业务不变量和结果。
5. 回退或恢复：说明反向脚本、备份恢复或不可逆情况下的替代办法。

## 5. MOM 数据规则

数据库表的存在不等于该系统拥有业务事实。库存余额应由库存事务等受控事实产生；质量判定不等于库存已经移动；追溯投影不能覆盖 MES、WMS、QMS 等业务域权威记录。

需要纠正已经发生的业务历史时，优先使用领域允许的冲销、反向事务、补偿或更正记录。直接覆盖历史字段必须有明确业务授权、审计和追溯处理。

## 6. 验证与交付

在隔离副本或代表性测试库验证零命中、单条、批量、中断、重跑、重复执行和回退。保存脚本校验和、schema 版本、预计/实际行数、耗时、锁影响和对账结果。开发完成只表示脚本具备受控执行条件，不等于授权在生产运行。
