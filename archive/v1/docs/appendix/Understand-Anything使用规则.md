# Understand Anything 使用规则

## 1. 使用目的

Understand Anything 用于构建代码库知识图谱，帮助开发人员理解文件、模块、类、函数、数据库对象、接口及其关系。图谱是导航和分析证据之一，不替代代码、DDL、配置、运行日志和测试等权威事实。

Codex 中使用 `$understand` 调用该能力。首次中文分析的参考形式为：

```text
$understand --language zh
```

强制忽略既有图谱并重建时使用 `--full`。正常维护优先复用已有图谱并按工具能力增量更新，避免每个局部任务都重复全量分析。

## 2. 必须构建或刷新图谱的情况

- 开发人员首次接触大型或陌生项目。
- 新增模块、跨模块/跨服务变更或全新项目建设。
- 项目文档不足，无法可靠判断入口、调用链和数据关系。
- 生产幽灵缺陷、复杂偶发问题或影响链不清。
- 现有图谱对应提交早于任务基线，且差异可能影响当前分析。

## 3. 可以采用定向分析的情况

- 稳定复现且范围明确的局部缺陷。
- 单个组件、方法或配置的可逆小改动。
- 已有最新图谱，并且本次只影响已知局部路径。

定向分析至少包括代码检索、定义与引用、调用链、相关测试、历史提交和适用的 DDL/接口检查，不能只阅读任务直接点名的一个文件。

## 4. 图谱有效性检查

使用图谱前检查项目元数据中的 Git 提交哈希、分析时间、文件数量和警告。图谱提交与任务基线不一致时先增量更新；无法更新时在开发方案中注明差异，并对相关区域重新做定向核验。

图谱发现的关系需要回到源码或配置确认，尤其是运行时反射、动态路由、配置注入、SQL 拼接、消息订阅和外部系统调用。图谱没有展示某条关系，不代表运行时一定不存在。

## 5. 任务证据记录

最终开发方案只需记录图谱对应的项目、提交哈希、分析日期、使用方式和与任务有关的关键结论，无需提交全部中间分析或 AI 对话。知识图谱文件是否纳入仓库由项目规则决定。

## 6. 安全与维护

分析前按项目 AI 数据规则排除密钥、生产数据、客户敏感资料、生成制品和无关大文件。全量或增量分析失败时必须报告缺失范围，不能把部分图谱声称为完整视图。
