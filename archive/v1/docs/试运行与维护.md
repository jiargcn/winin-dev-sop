# 试运行与维护

## 1. 当前交付状态

本规范已经完成总入口、场景分类、风险分级、通用质量门禁、18份独立场景流程、最终产物模板以及 Java/Vue/PostgreSQL/GitHub/Understand Anything/MOM 附录。当前版本覆盖个人开发人员从领取任务到完成方案、编码、自测和交付准备的完整范围。

正式测试管理、上线审批、部署执行和生产运维不属于主体流程。数据脚本、热修和安全缺陷文档只定义开发阶段证据与交付条件，不授予生产操作权限。

## 2. 已固定的约束

- 每项任务只能选择一个主场景，可以叠加多个风险标签。
- `L3` 任务在主体编码前必须完成人工开发方案评审。
- AI 数据使用按项目规则执行；没有项目规则时禁止输入密钥、凭据、未脱敏生产数据和客户敏感信息。
- 不保存完整 AI 对话，只保存风险等级要求的最终方案、代码、测试和结论。
- Java 17、Spring Boot 3、Maven、JUnit 5、Mockito、Vue 3、Vitest、PostgreSQL、GitHub Actions 是当前默认技术基线。
- 自动化测试薄弱不能成为跳过验证的理由，本次变更范围必须建立特征测试、回归测试或可重复人工验证。

## 3. 代表性选路验收

| 任务样例 | 主场景 | 风险标签 | 最低等级 | 选择理由 |
| --- | --- | --- | --- | --- |
| 在现有 WMS 新增库内移位申请与执行闭环 | `REQ-01` | `DATA`、`MOM-DOMAIN` | `L3` | 新增可独立验收能力并改变库存相关数据 |
| 修改生产工单报工后的状态推进规则 | `REQ-02` | `MOM-DOMAIN`、`COMPATIBILITY` | `L3` | 改变现有业务状态且涉及在途与历史对象 |
| 优化 PDA 扫码页面，减少操作步骤但不改业务结果 | `REQ-03` | 视防重影响增加 `MOM-DOMAIN` | `L1/L2` | 主要目标是交互效率，风险由是否影响业务执行决定 |
| 将出库查询 P95 从既定基线优化到目标值 | `REQ-04` | `PERFORMANCE`、可能的 `DATA` | `L2/L3` | 新性能目标要求基线、负载和正确性对账 |
| 同一输入每次都触发空指针异常 | `BUG-01` | 按影响添加 | `L1/L2` | 可以形成修复前失败的稳定回归测试 |

| 消息偶发重复消费且已有完整链路日志 | `BUG-03` | `CONTRACT`、`CROSS-MODULE` | `L3` | 偶发但已有证据，可通过假设验证定位 |

| 库存事务与余额对账不一致 | `BUG-05` | `DATA`、`MOM-DOMAIN` | `L3` | 需确认权威事实、根因、存量修复和对账 |
| 高峰期出现数据库死锁和接口超时 | `BUG-06` | `PERFORMANCE`、`DATA` | `L3` | 需要可控时序、锁分析和业务正确性验证 |

这些样例用于验证分类规则，不代表特定项目事实。真实任务仍须根据项目代码、DDL、规则和数据重新判断。

## 4. 首轮真实任务试运行

建议选择一项 `REQ-01/REQ-02`、一项 `BUG-01` 和一项 `BUG-03/BUG-04` 进行试运行。开发人员不依赖文档作者解释，独立完成场景选择、风险分级、上下文准备、方案、测试、自测和 Pull Request 描述。

试运行只收集以下反馈：

- 是否能在五分钟内选择唯一主场景和全部风险标签。
- 是否存在步骤无法执行，原因是资料、权限、工具还是文字不清。
- 最终产物是否足够支持开发方案评审和提交测试。
- 哪些步骤重复、缺失或无法产生可观察证据。
- 实际耗时与原有方式相比如何，返工或漏测是否减少。

反馈应集中到一个规范维护任务中，不为每个问题创建独立说明文档。

## 5. 修订规则

修改本规范时先更新[场景分类与选路](场景分类与选路.md)和[通用规则与质量门禁](通用规则与质量门禁.md)的权威口径，再同步所有受影响场景。新增数据库、框架或工具时优先增加附录；只有主要工作方法发生变化时才新增场景。

每次发布前重新执行 Markdown 结构、相对链接、18个场景覆盖、13类流程内容和未完成标记检查。技术栈版本、外部标准和工具命令具有时效性，应由规范维护人定期核验官方资料。

## 6. 下一步

当前唯一需要外部完成的验收是使用真实公司任务进行试运行。完成三个代表性任务后，根据集中反馈修订一次，再将该版本作为公司推广基线。
