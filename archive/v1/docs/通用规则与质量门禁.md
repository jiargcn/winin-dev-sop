# 通用规则与质量门禁

## 1. 适用范围与责任

本规范面向独立处理开发任务的开发人员。AI 可以协助检索、归纳、提出假设、设计方案、生成代码和测试、分析差异，但不能替代任务责任人确认业务意图、批准高风险方案或判断测试是否充分。

开发人员必须能够解释最终代码为什么符合需求、为什么不破坏既有行为、测试覆盖了哪些风险以及哪些结论尚未验证。无法解释的 AI 生成内容不得进入正式变更。

## 2. AI 数据边界

每个项目应维护可使用 AI 的数据范围。任务开始时必须确认当前项目规则，并在任务最终产物中记录采用的边界。

项目没有明确规则时采用以下默认限制：

- 禁止向外部 AI 提交密钥、口令、令牌、证书、连接串和个人凭据。
- 禁止提交未脱敏的生产数据、客户敏感信息、个人信息和受合同限制的资料。
- 日志只提供定位问题所需的最小片段，并替换姓名、账号、手机号、地址、唯一码等可识别内容。
- 代码、DDL、接口文档是否可提交由项目授权决定；无法确认时只使用本地工具和最小代码片段。
- AI 建议执行命令、访问环境或修改数据时，开发人员必须检查目标、影响和可恢复性。

## 3. 事实、推断和假设

AI 协作过程中应区分以下信息：

| 类型 | 定义 | 处理方式 |
| --- | --- | --- |
| 已确认事实 | 由任务单、代码、DDL、配置、日志、测试或人员确认直接支持 | 可以作为设计与实现依据，保留来源 |
| 推断 | 由多个事实合理推出但尚未直接验证 | 明确标记，并通过代码、测试或运行证据验证 |
| 假设 | 为继续工作临时采用的前提 | 记录影响、验证方法和不成立时的处理方式 |
| 待决策 | 存在多个真实选项，且选择会改变总体方案 | 停止相关实现，提交选项和建议，由有权人员决定 |

不得把 AI 根据命名、代码风格或行业惯例猜出的结论写成项目事实。任务描述、代码、数据库和实际运行行为相互冲突时，应保留冲突并确认权威来源。

## 4. 通用八阶段流程

### 阶段一：任务准入

确认任务目标、业务价值、提出人、验收标准、范围外内容、目标版本和交付时间。选择唯一主场景、风险标签与等级，核对 AI 数据边界。信息不足且会改变总体方案时，不进入编码。

### 阶段二：建立可靠基线

确认正确仓库、分支和基线提交，检查工作区已有改动并避免覆盖他人工作。完成依赖准备、基础构建和必要的现有测试，记录基线本身已经存在的失败。缺陷任务还应固定问题发生版本、环境和数据条件。

### 阶段三：准备上下文

按任务范围读取项目说明、架构决策、相关代码、测试、DDL、接口契约、配置、日志和历史变更。首次接触大型代码库、跨模块变更、新模块、文档严重缺失或幽灵缺陷，应构建或刷新 Understand Anything 知识图谱；局部任务使用定向检索即可。

知识图谱必须记录所对应的 Git 提交。图谱落后于任务基线时先增量更新；无法更新时只能作为线索，不能作为当前事实证据。

### 阶段四：分析与开发方案

先描述当前行为、目标行为和差距，再确定影响范围、实现边界、数据与接口变化、兼容策略、失败处理和回退方式。测试设计必须在主体编码前完成，用于证明方案可验证，而不是编码完成后的补充说明。

`L1` 可以使用简版方案并自审；`L2` 必须保留正式开发方案；`L3` 必须在主体编码前完成人工评审。评审后方案发生实质变化时重新评审受影响部分。

### 阶段五：测试基线

自动化测试薄弱的存量项目，应先建立能够固定当前正确行为的特征测试或可重复验证脚本。稳定缺陷优先编写修复前失败的回归测试。无法自动化时，必须写出环境、数据、操作步骤和可观察结果，保证他人可以重复。

### 阶段六：限界实现

把变更拆为可验证的小步，每一步只解决一个明确目标，并在完成后运行最近层级的测试。不得顺手重构无关代码、升级无关依赖或修复未进入任务范围的问题。发现新问题时记录并单独建项，除非它阻断当前任务。

### 阶段七：审查与自测

先执行确定性的编译、单元测试、静态检查和构建，再让 AI 基于最终差异、任务目标和风险标签进行审查。AI 审查必须关注正确性、安全、兼容、异常路径、测试缺口和无关改动；开发人员逐条判断，不得批量接受建议。

完成相关 JUnit 5/Mockito、Vitest、Maven、npm 构建和项目规定的集成验证。GitHub Actions 是提交后的确定性门禁，不能用 AI “看起来正确”的结论代替。

### 阶段八：交付准备

更新任务所需的最终产物，整理 GitHub Pull Request 描述，注明影响范围、测试结果、DDL/接口/权限/兼容变化、部署或数据执行前提、未验证项和剩余风险。确认没有调试数据、临时开关、跳过测试配置和敏感信息后，才能提交下一环节。

## 5. MOM 领域质量门禁

命中 `MOM-DOMAIN` 时，开发方案和测试必须回答以下问题：

- 业务意图从哪里产生，谁接受或批准，谁执行，结果由谁确认。
- 哪个对象表示计划或待执行任务，哪个对象固化已经发生的业务事实。
- 状态如何正常推进，以及如何撤销、关闭、冲销、返工或补偿。
- MES、WMS、QMS、EAM、ANDON、SCP 与相邻系统分别拥有哪些权威事实，哪些只是引用或查询投影。
- 库存预期、库存事务和库存余额是否被正确区分；质量判定是否被错误地当成实际库存移动。
- 跨域失败后如何恢复、对账和防止重复执行，历史及追溯链是否保留。
- 验收时是否能够从来源正向核对结果，并从结果反向追溯来源。

两个系统可能写入同一事实时，必须停止扩展实现，明确主系统、冲突条件、写入门禁和对账方式。不得用“双向同步”掩盖事实所有权未决。

## 6. 通用测试维度

所有场景按适用性选择以下测试维度：

| 维度 | 最低要求 |
| --- | --- |
| 正常路径 | 验证主要业务目标从输入走到可观察结果 |
| 边界与校验 | 空值、极值、重复、非法状态、时间边界、精度和分页 |
| 异常与恢复 | 超时、依赖失败、部分成功、重试、撤销、回滚和补偿 |
| 状态与数据 | 合法状态转换、不变量、事务、并发和执行后对账 |
| 权限与安全 | 未登录、无权限、跨角色、跨租户、敏感字段和注入风险 |
| 兼容与回归 | 历史数据、旧调用方、默认行为、相关功能和回退版本 |
| 前端交互 | 加载、空态、错误态、重复提交、按钮状态、刷新和多窗口 |
| 可观测性 | 日志级别、关联标识、错误信息、指标和敏感信息脱敏 |

## 7. 人工评审门禁

以下情况必须在主体编码前进行人工开发方案评审：

- PostgreSQL DDL、数据迁移、批量修复或不可逆数据影响。
- 公共 API、消息、文件格式或外部调用契约变化。
- 认证、授权、租户隔离、个人信息、密钥或安全边界变化。
- 库存、生产、质量、设备、异常响应、协同或追溯等关键业务事实变化。
- 跨服务事务、一致性、并发、高容量或难以回退的变化。
- 生产紧急修复，允许先做压缩版评审，但必须事后补齐正式结论。

评审至少确认目标和范围、当前与目标行为、影响范围、关键决策、测试策略、兼容方式、数据处理、失败恢复与回退。评审通过不等于代码正确，仍须完成实现后的差异检查和自测。

## 8. 统一阻断项

出现以下任一情况时不得声称开发完成：

- 验收标准无法观察，或者任务提出人与代码表达的业务规则冲突且未确认。
- 高风险事实所有权、数据迁移、接口兼容或权限边界尚未决定。
- 基线测试失败与本次变更引入失败没有区分。
- 关键异常路径没有测试或可重复验证步骤。
- 最终差异中存在不明来源代码、无关修改、跳过测试、硬编码密钥或未脱敏数据。
- `L3` 任务没有人工方案评审结论。
- 测试或 GitHub Actions 未执行且没有记录原因、影响与接续责任。

## 9. 完成定义

开发完成必须同时具备：任务与场景选择正确；方案满足风险等级；代码差异受控；适用测试通过；风险标签专项检查完成；最终产物完整；剩余风险透明。详细记录要求参见[模板索引](templates/README.md)，工具命令参见[技术栈附录](appendix/README.md)。

安全开发底线参考 [NIST Secure Software Development Framework](https://csrc.nist.gov/projects/ssdf)。AI 代码审查的编译、测试、静态分析和人工核对原则参考 [GitHub Review AI-generated code](https://docs.github.com/en/copilot/tutorials/review-ai-generated-code)。
