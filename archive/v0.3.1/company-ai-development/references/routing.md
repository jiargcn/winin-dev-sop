# 自动选路规则

## 使用方法

根据任务的主要交付结果选择一个主场景。先根据任务原文判断，再用代码、数据和验收标准验证。不要仅根据任务标题分类。

## 决策顺序

1. 如果目标是建立一个新项目或首个可端到端验收的业务切片，选择 `E`。
2. 如果目标是修复不正确的系统行为，能够稳定复现选择 `B`，无法稳定复现选择 `C`。
3. 如果目标是改变用户或业务可观察行为，选择 `A1`、`A2` 或 `A3`。
4. 只有业务可观察行为原则上保持不变，主要交付物是技术资产变化时，选择 `D`。

## 需求子类

| 场景 | 判断 |
| --- | --- |
| `A1` | 增加此前不存在、可以独立验收的业务能力 |
| `A2` | 改变现有页面操作、查询、计算、规则、流程、状态或结果 |
| `A3` | 只修改文字、样式、排序或静态展示，不影响后端、接口、数据、权限和业务结果 |

发现 A3 需要修改后端、接口、数据、权限或业务含义时，自动改为 A2，不询问是否继续走快速流程。

## 容易混淆的任务

| 任务 | 场景 |
| --- | --- |
| 修复错误的历史数据 | B 或 C，并增加数据库信号 |
| 因新规则迁移历史数据 | A1 或 A2，并增加数据库信号 |
| 因技术架构调整迁移数据且业务语义不变 | D，并增加数据库信号 |
| 新增接口字段支持新业务规则 | A1 或 A2，并增加接口信号 |
| 只升级驱动且业务语义不变 | D |
| 性能不符合已确认指标 | B 或 D，取决于这是缺陷还是专项优化任务 |

## 置信度

- `high`：任务目标、验收标准和现状证据指向同一场景。
- `medium`：场景基本明确，但尚缺不会改变主场景的资料。
- `low`：需求与缺陷、A3 与 A2、业务变化与工程变化之间存在冲突。

`high` 自动继续；`medium` 可以继续只读分析；`low` 必须提出最少确认问题。
