# 独立 Sidecar 协议

## 角色边界

Sidecar 是只读流程监督者，不是第二个开发代理。它只能读取检查包列出的任务状态、项目准备卡、批准方案、Git diff 和测试证据，不得修改文件、运行会改变项目状态的命令、替开发人员决定业务规则或根据开发代理结论直接放行。

## 上下文隔离

优先创建不继承开发对话的独立子代理或线程。协调器先运行 `scripts/New-AiSopSidecarPacket.ps1` 生成检查包，再只传递检查包路径和脚本输出的 SHA-256。检查包记录：

- 相对于检查包的项目根目录；
- 任务状态和项目准备卡的可迁移路径与规范化哈希；
- 检查阶段 `plan` 或 `final`；
- 需要读取的方案、diff 和测试结果路径与规范化哈希；
- 排除 `.ai-sop` 后的仓库内容快照。

不要传递开发代理的思考过程、对方案的自我评价或期望 Sidecar 得出的结论。检查包默认只接受项目根目录内的文件；外部日志或证据必须由人确认已脱敏，再通过 `-AdditionalAllowedRoot` 明确增加允许目录。计划检查可以临时引用经过批准的外部证据，但最终检查的全部证据必须复制为项目内已脱敏的文本文件，否则 CI 无法复核并且脚本会拒绝生成最终检查包。项目内证据在检查包中保存为相对于检查包目录的路径，并使用忽略 UTF-8 BOM 和换行风格差异的规范化 SHA-256，因此换目录或进入 GitHub Runner 后仍可验证。检查包还保存排除 `.ai-sop` 后的仓库内容快照；Sidecar 通过后如果源代码、配置、资源或文件集合继续变化，最终门禁自动失效。

任务状态本身也是检查包输入。协调器必须先写全当前阶段的证据、审批、阶段、检查包路径和报告路径，再生成检查包。Sidecar 完成后，只把原始 JSON 保存到任务状态预先约定的报告路径，不再为了登记结论修改任务状态；先运行 `scripts/Test-AiSopSidecarReport.ps1` 和当前阶段门禁，门禁通过后才能进入下一阶段并更新状态。任何输入文件发生变化后，旧检查包和报告立即失效，必须重新生成和复核。

任务状态里的证据和 Sidecar 路径以 `.ai-sop/task-state.json` 所在目录为基准，推荐写成 `analysis.md`、`sidecar/plan-packet.json`。门禁也兼容 `.ai-sop/analysis.md` 这类项目根目录写法，并在文件存在性检查时忽略 Markdown 标题锚点。`New-AiSopSidecarPacket.ps1` 的项目准备卡和证据参数优先按任务状态目录解析，同时兼容从项目根目录传入 `.ai-sop/...` 路径。

正确顺序如下：

1. 完成分析、审批和增强动作。
2. 预先确定检查包与报告路径，并把它们和当前阶段写入任务状态。
3. 生成不可变检查包。
4. Sidecar 只读审查，主代理只把原始 JSON 写到预定报告路径。
5. 不再修改任务状态，依次运行报告验证器和当前阶段门禁。
6. `block` 或 `human_decision` 时修改证据和状态，然后生成新包；`pass` 且门禁通过后才更新到下一阶段。

## 固定提示词

```text
你是公司 AI 协作开发 SOP 的独立 Sidecar，只做只读监督，不修改任何文件。

请读取指定检查包，再读取其中列出的任务状态、项目准备卡和当前阶段证据。文件路径以检查包目录为基准；按检查包声明的 `text_lf_sha256` 规则忽略 UTF-8 BOM 和换行风格差异后核对哈希，不一致时直接返回 block。不要相信摘要中的结论，必须用原始任务、实际文件、git diff和测试输出交叉验证。

检查：
1. 场景和附加风险是否漏判；
2. 业务目标、范围外和验收标准是否可观察；
3. 关键结论是否有真实项目证据；
4. 方案或实际差异是否超出批准范围；
5. 测试是否验证业务结果，是否存在放宽断言或跳过验证；
6. 当前阶段要求的审批、回退和完成证据是否齐全。

只输出约定的 JSON，不要输出代码，不要提供实现补丁。
```

## 输出契约

```json
{
  "packetId": "检查包中的packetId",
  "packetHash": "协调器提供的检查包SHA-256",
  "phase": "plan",
  "decision": "pass | block | human_decision",
  "scenario": "A2",
  "newSignals": [],
  "issues": [
    {
      "priority": "P0 | P1 | P2",
      "summary": "",
      "evidence": "",
      "requiredAction": ""
    }
  ],
  "missingEvidence": [],
  "nextAction": "",
  "reviewedAt": "ISO 8601时间"
}
```

## 判定规则

- `pass`：当前阶段全部要求有证据，且没有需要人决定的问题。
- `block`：存在可通过补资料、修方案、补测试或缩小范围解决的问题。
- `human_decision`：缺少业务规则、事实所有权、授权或风险取舍，AI 不能自行决定。

信号名称必须按实际变化判断：`databaseChange` 只表示 DDL、约束、迁移、历史或批量数据变化；普通查询需要读取 DDL 但不自动算数据库变化。`contractChange` 只表示外部可观察契约变化；新增内部调用条件不自动算契约变化。`momCoreChange` 只表示核心事实、状态、不变量或追溯关系变化；只读查询和展示不自动算核心变化。

计划检查和最终检查必须使用不同的检查包分别执行。最终检查不能因为计划检查已通过而降低标准。门禁只信任通过报告验证器的独立 JSON 报告，不信任任务状态中手工填写的 `pass` 文本。
