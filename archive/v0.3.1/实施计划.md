# 公司 AI 协作开发 SOP 系统实施计划

## 1. 建设目标

建设一个以公司级 Skill 为统一入口、以项目准备卡为项目事实来源、以独立只读 Sidecar 为过程监督、以 PowerShell 脚本和 GitHub Actions 为确定性门禁的 AI 协作开发 SOP 系统。开发人员不需要记忆场景编号、提示词和检查顺序，只负责业务目标、关键规则、方案取舍、关键代码和最终业务结果。

## 2. 系统组成

| 组成 | 责任 | 不承担的责任 |
| --- | --- | --- |
| 公司级 Skill | 任务初始化、自动选路、流程调度、按需加载 SOP、组织证据 | 不替代业务决策，不提供强制门禁 |
| 项目准备卡 | 提供项目命令、资料来源、负责人、AI 数据边界和 CI 要求 | 不保存具体任务过程 |
| 开发代理 | 分析、编码、测试和修正 | 不审查并批准自己的最终结果 |
| Sidecar | 独立只读检查选路、方案、差异和证据；报告绑定输入哈希 | 不修改代码，不发明业务事实 |
| 确定性脚本 | 建立状态、采集上下文、检测风险、验证门禁、生成报告 | 不判断未知业务规则 |
| GitHub Actions | 在提交后重复验证流程证据和项目检查 | 不以 CI 通过代替业务验收 |

## 3. 实施阶段

### 阶段一：可运行 Skill 基础

交付统一入口 Skill、七类场景 SOP、自动路由规则、项目准备卡、任务状态协议和 Sidecar 协议。验收标准是 Skill 能根据任务资料选中唯一主场景，只加载相关 SOP，并明确下一步和缺失资料。

### 阶段二：确定性脚本

交付任务初始化、项目上下文采集、风险信号检测、状态更新、门禁校验和完成报告脚本。验收标准是脚本能在无 Git、干净 Git 和存在变更的项目中给出明确结果，失败时返回非零退出码且不破坏现有文件。

### 阶段三：独立 Sidecar

在编码前和编码后各执行一次独立只读复核。Sidecar 只接收任务状态、项目准备卡、方案、差异和测试证据，不继承完整开发对话。验收标准是 Sidecar 能阻断缺失验收标准、范围扩大、测试证据不足和高风险审批缺失。

### 阶段四：CI 与公司分发

提供 GitHub Actions 模板、项目初始化说明和公司分发方案。验收标准是 Pull Request 中缺少有效 SOP 证据时 CI 失败，证据齐全时通过；Skill 可以作为仓库 Skill 或公司内部插件分发。

### 阶段五：试点和改进

选择 A3、A2、稳定缺陷、难复现缺陷和依赖升级进行前向测试，覆盖 AI 使用经验不同的开发人员。观察选路耗时、人工提问数量、无关修改、测试遗漏和返工情况，再调整 SOP。目标不是一次做到最复杂，而是先让常见任务明显减少流程操作和返工。

## 4. 完成判定

只有以下证据全部存在时，系统建设才算完成：

- Skill 结构校验通过；
- 七类场景可唯一选路且都能独立推进；
- 项目准备卡和任务状态具有可验证 Schema；
- Sidecar 具备独立上下文、只读约束和结构化输出；
- 所有确定性脚本通过自动测试；
- GitHub Actions 模板能对通过和失败样例作出正确判断；
- 代表性任务前向测试通过并记录发现的问题；
- 入口文档能够让开发人员从任务开始，不需要阅读旧版长规范。
- 至少一个真实 MOM 项目完成端到端任务和真实 GitHub Pull Request 门禁验证；
- 不同 AI 使用经验的开发人员完成试用，试点问题已经回写 Skill、准备卡或脚本。
