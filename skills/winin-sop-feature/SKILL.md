# 功能开发（入口）

## 触发即获工作流

本 skill 是功能任务的唯一入口（含新增功能与现有功能修改）。用户触发本 skill 后，按以下流程执行；任务协议、状态机、门禁、纪律等共享规则见共享契约 `../winin-sop-common/workflow.md`。

## 流程总览

```mermaid
flowchart LR
    A["① 调研并推荐档位（人工确认）"] --> B["② 需求澄清（有预算）"]
    B --> C["③ 方案提案 + 写 prd/design"]
    C --> D["方案确认"]
    D --> E["④ 实施"]
    E --> F["⑤ 单元测试（winin-sop-test）"]
    F --> G["⑥ diff 审查（winin-sop-review）"]
    G --> H["静默通过 / 异议讨论"]
    H --> I["收尾：archive 仅用户主动"]
```

## ① 调研并推荐档位（人工确认）

- 快速只读调研（有上限）：定位入口和涉及文件 → 硬性信号扫描（数据库/公共接口/MOM/安全/跨服务）→ 规模估计。命中硬性信号立即停止调研。
- 找到最接近的现有功能作为锚点（"复用 X / 新增 Y / 不同 Z"）。
- 展示调研摘要 + 推荐档位 + 理由，请开发人员确认或调整。
- 命中硬性信号 → 自动置 `independentReview: true`，并在调研摘要里用自然语言带过（如"涉及数据库变更，交付前会加一道独立把关"），不要求用户理解或选择"独立复核"机制。
- 用户表达更谨慎的意愿（"仔细一点""稳妥些""不放心"）→ 置 `independentReview: true`。
- 确认结果在 ③ 建任务时登记进 task-state.json（见 ../winin-sop-common/workflow.md task-state.json 段；L1 不建任务）。

档位决定产物：L1 直接改（git diff 即记录）；L2 = task-state.json + prd.md + design.md。命中硬性信号 → 置 independentReview: true，交付前加独立复核。

## ② 需求澄清（有预算）

目标：用最少的问题拿到足够开始设计的输入；足够开始设计就停，禁止无限追问。

### 禁止假设（铁律）

业务事实（规则、口径、验收标准）禁止任何形式的猜测，包括"合理假设"。错误假设会静默进入代码，代价远高于多问一句。

事实只能来自三个渠道：

1. 查证：代码、配置、文档、现有实现有证据 → 查证后作为事实，不问。
2. 询问：查不到且会改变业务结果 → 必须问（选项式，2-4 个选项）。
3. 用户豁免：用户明确说"先按 X 做" → 记录为人工豁免（授权方 + 影响 + 补验动作），不是假设。

查不到也问不到（用户不知情）→ 任务进入 `blocked`，写明缺什么、谁提供、恢复条件。

工程决策（实现方式、命名、展示细节）不属于业务事实，由方案提案/方案确认可见化。

### 提问预算（动态 3~5 轮）

1. 每问先过测试："这个事实，不问能否开始设计？"能查证的查，不问；查不到且会改变结果的问；查不到且不影响结果的（工程决策）自定并写入 design。
2. 动态轮数：预算 3~5 轮，按任务复杂度浮动：
   - 3 轮起步（默认）：锚点清晰、业务规则可从查证确认的任务；问满该问的即停。
   - 追加到 4~5 轮：业务规则多源/跨模块/口径歧义大，或用户资料不全时，逐轮追加，每轮仍一次一问。
   - 达到"足够开始设计"标准即停（见下），不因有预算就多问；最多 5 轮，问完即止。
3. 待确认项：预算内未问完的必要事实写入 prd.md"待确认项"段，编码前必须清零，方案确认时逐条裁决或豁免，不允许带着未确认项编码。

### 澄清节奏

- 一次一问，选项式；锚点+差异问法（只问"与锚点的差异"）。
- 每个确认立即写入 prd.md，不攒到最后。

### 足够开始设计的判断标准（达到即停）

- ✓ 目标可描述；✓ 关键业务规则已确认（全部来自查证/询问/用户豁免）；✓ 验收标准可生成（覆盖矩阵五格：主流程/必填与边界/权限/失败处理/原功能回归）；✓ 涉及文件/接口已定位。

## ③ 方案提案 + 建任务 + 写 prd/design

- 方案提案（中等以上复杂度）：给出 2-3 个实现方案，各带权衡（改动面/风险/兼容），标出推荐项并说明理由；用户选定（或“按你推荐的来”）。简单任务（1-2 个文件）跳过提案。
- 大任务拆解：任务跨多个服务、同时涉及前后端与数据库、包含多个可独立验收结果时，建 `subtasks.md` 拆 2~5 个同级子任务（目标/涉及文件/依赖/对应 AC/验证方式），清单与执行顺序随方案一并确认（见 ../winin-sop-common/workflow.md「大任务拆解」）。
- 建任务并登记档位：`node ../winin-sop-common/scripts/winin-sop.mjs init --repo <root> --task <编号> --title <标题>` → 编辑 task-state.json 的 complexity 字段（level/reason/confirmedBy/confirmedAt；字段模板见 ../winin-sop-common/workflow.md）
- 写 prd.md（目标/验收标准/范围外/待确认项/关键事实）+ design.md（现状证据复用调研/方案/实施步骤与验证/回退/规范依据）。
- 验收标准从已确认的业务规则自动生成（不是用户提供），覆盖矩阵五格；每条可观察、可验证。验收标准编号 AC1..ACn 是测试与验证记录的引用键（见 ⑥）。
- 加载规范：调用 `../winin-sop-spec/SKILL.md`（项目约定必加载，其余按索引命中）。

## ④ 方案确认

- 向开发人员展示目标、范围、修改位置、验收标准和风险；同时逐条裁决 prd.md"待确认项"。
- 确认后才编码；命中硬性信号 → 置 `independentReview: true`（如尚未）。

## ⑤ 实施

- 确认后开工：`node ../winin-sop-common/scripts/winin-sop.mjs status --repo <root> --task <id> --state in_progress`（自动校验 readiness 门：产物 + 方案确认，不过会拒绝并列出缺失项）。
- 最小端到端切片：界面或接口 → 服务 → 数据 → 权限。不顺带建设未验收的扩展能力。
- 每批修改后检查实际差异（git diff），确认只改了方案内内容。
- 范围扩大 → 停止，回到方案确认。

## ⑥ 单元测试

- 实施完成 → 调用 `../winin-sop-test/SKILL.md` 编写/运行单元测试。测试以 prd.md 验收标准为输入：每条 AC 至少映射一种验证方式（业务链单测 / design 验证步骤 / 人工验证）。
- 测试通过 → 把每条 AC 的验证记录登记到 review.md「验证记录」段（`- [x] ACn | 验证方式: ... | 结果: passed | 证据: ...`）；测试失败 → 回到实施修复，重跑后更新记录。
- 纯前端/仅展示改动按 design.md 验证步骤执行，不强制写单测（本 skill 单测范围 = 业务逻辑层），但验证结果同样登记到验证记录。

## ⑦ diff 审查

调用 `../winin-sop-review/SKILL.md`（唯一交付检查，静态只读）：prd 与实际改动逐条比对，逐文件检查调用方/接口契约/数据/权限/回退，检查需求遗漏/边界异常/代码卫生，核对验收标准证据与规定动作完成证据，spec 合规检查。`independentReview` 任务由独立只读上下文复核。

展示结果后不再请求确认，开发人员无异议则静默通过（有异议才回复），任务状态置 `ready_for_review`（`node ../winin-sop-common/scripts/winin-sop.mjs status --repo <root> --task <id> --state ready_for_review`；自动校验 completion 门，不过会拒绝并列出缺失项，补齐后重试）。

## 收尾

- 仅用户主动：`node ../winin-sop-common/scripts/winin-sop.mjs archive --repo <root> --task <id>`；用户说"归档"才执行。
- 共享规则（门禁/纪律/检索纪律）见 ../winin-sop-common/workflow.md。

## 示例

任务：工单列表新增按产线和计划日期组合筛选。

先定位现有筛选实现（锚点）、接口契约和索引 → 推荐档位确认 → 澄清只问"计划日期口径"（选项式），产线下拉/组合逻辑从现有 Mapper SQL 查证 → 方案提案（扩展 DTO+动态 SQL 推荐 / 新建接口 / 前端过滤）→ 验收标准自动生成（组合交集/原筛选回归/自然日边界/空值不过滤）→ 确认后实施 → 回归验证 → diff 交付。
