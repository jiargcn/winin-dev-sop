# 单元测试环节

## 核心思想

一个测试用例 = 一条完整业务链，而不是一个方法。

```
写流程用例（默认）           写小逻辑单测（例外）
─────────────────           ─────────────────────
创建申请 → 提交 → 审批 →      仅当流程用例失败后、
处理 → 生成任务 → 执行 →      定位到具体环节时才写，
落账 → 对账                  用于深入诊断，不替代流程用例
```

四条铁律：

1. 真实上下文：`@SpringBootTest` 加载模块全部 Bean，Service/Mapper/事务/租户插件/AOP 真实执行；
2. 真实数据：数据库跟随当前激活 profile，不用 H2 假库；
3. 跨服务不 mock：Feign API 通过注册中心路由到真实服务实例，主数据取真实值；
4. 隔离靠回滚：每个用例 `@Transactional`，结束自动回滚，不留脏数据、不占流水号。

## 测试输入：prd 验收标准（先读 prd 再写测试）

测试以 `prd.md` 的验收标准为输入：

1. 写测试前先读任务 `prd.md`「验收标准」段，逐条列出 AC1..ACn；每条 AC 对应一种验证方式。
2. 验证方式三选一：业务链单测（本 skill 默认，覆盖业务规则类 AC）、design.md 实施步骤中的验证命令（纯前端/仅展示类 AC）、人工验证（页面/数据检查，记录操作步骤）。
3. 测试/验证执行后，把每条 AC 的验证记录登记到任务 `review.md`「验证记录」段：
   ```text
   - [x] AC1 | 验证方式: mvn -o -pl win-module-wms test -Dtest=OrderFlowTest | 结果: passed | 证据: design.md 验证记录 #1
   ```
   结果取值 `passed` / `failed` / `skipped`；`skipped` 必须注明原因（追加“原因: ...”）。
4. completion 门机械校验：每条已勾选 AC 必须有对应验证记录；无 failed；skipped 需说明原因。缺记录、留 failed 都过不了门（见 ../winin-sop-common/workflow.md 门禁段）。
5. 无法自动验证的 AC（如人工回归）也必须在验证记录中登记验证方式与结果，不允许静默跳过。

## 环境就绪检查（跑用例前必须逐项通过）

> 具体连接信息/配置位置见项目规范（winin-sop-spec 加载的排查类规范），不假设任何一处必有。

| # | 检查项 | 说明 |
|---|--------|------|
| 1 | 数据库可达 | 按 profile 连接信息执行连通性查询（如 `select 1`） |
| 2 | 依赖中间件可达 | Redis 等测试用中间件 ping 通 |
| 3 | 注册中心依赖服务已注册 | 依赖的服务实例 healthy（如 Nacos 服务列表） |
| 4 | schema 与代码一致（高频坑） | 本地库可能落后于 DO 定义：DO 有新列而表里没有 → 第一条 SQL 就 `BadSqlGrammar`。先跑一个冒烟查询，按报错表与代码 DO/线上库对齐补列，再跑用例 |
| 5 | 关键业务配置取真实值 | 如业务类型/开关配置决定流程步骤，不要假设默认值，先查真实配置再按状态机推进 |

## 编写规范

### 用例结构（Given-When-Then）

```java
@Test
void 业务意图_中文描述() {
    // Given：主数据（跨服务真实获取）
    ItembasicRespDTO item = itembasicApi.getOne(req).getCheckedData();
    // When：业务链操作（真实 Service 调用）
    String number = service.create(vo);
    // Then：真实落库断言（Mapper 查询 + 状态机 + 副作用）
    assertNotNull(mapper.selectOne(...));
}
```

### 命名

- 测试类：`{业务}FlowTest`
- 测试方法：`{业务意图}_{预期结果}`，中文描述业务链
- 一个方法一条完整链，禁止把链拆成多个测试方法（事务回滚会断链）

### 断言口径

| 层 | 断言对象 | 标准 |
|----|----------|------|
| 单据 | 主表状态 | 状态机逐步断言（每步操作后断言下一步状态） |
| 落账 | 明细/流水表 | 数量、金额与操作输入一致，按业务号查询 |
| 对账 | 余额/汇总表 | 前后快照差值 = Σ(本次操作量) |
| 副作用 | 关联表 | 任务/记录/日志生成、状态联动 |

### 主数据策略

- 优先从真实数据反查（如从余额表查有库存的组合），保证主数据真实存在；
- 或用例内通过 Feign 查询并 `assertNotNull`（数据不存在时用例明确失败，而不是静默跳过）；
- 禁止硬编码"看起来存在"的主数据，校验链会真实打到下游。

## 运行命令

```bash
# 测试编译（先编译，快速暴露编译错）
mvn -o -pl <模块> test-compile -DskipTests
# 跑单个流程用例
mvn -o -pl <模块> test -Dtest=<Xxx>FlowTest
# 跑全部流程用例
mvn -o -pl <模块> test -Dtest="*FlowTest"
```

- 离线 `-o`：代理干扰 HTTPS 下载时用本机 m2 仓库（见项目构建指南）。
- 运行结果（通过/失败、覆盖的命令输出）记录为验收标准证据，写入 design.md 验证记录。

## 流程失败后的诊断流程（小逻辑单测的唯一合法场景）

```
1. 流程用例失败 → 从失败断言/异常定位业务环节（哪一步、哪张表、哪个校验）
2. 环节内逻辑复杂时，才写小逻辑单测深入诊断：
   @Tag("diagnosis") class XxxDiagnosisTest { ... }
3. 修复后：诊断单测保留为回归（注释标注「来源于 XxxFlowTest 失败诊断」），
   但主防线仍是流程用例；删除诊断单测可接受，删除流程用例不可接受
```

> 为什么禁止把小逻辑单测当主测试：碎片化用例只验证"默认参数下不抛异常"或"单段逻辑"，对业务正确性零保障；流程用例失败前，它们既不能发现回归，也不能证明业务可用。

## 已知环境问题与处理

| 问题 | 现象 | 处理 |
|------|------|------|
| 本地库 schema 落后 | `BadSqlGrammar: 字段 X 不存在` | 与 DO/线上库对齐补列后重跑 |
| 事务中止连锁报错 | `SQL state [25P02] 当前事务已中止` | 看日志中最早的 SQL 错误，修复后重跑 |
| 业务配置与假设不符 | 断言状态与预期不符 | 先查真实配置，按状态机推进，不写死步骤 |
| 跨服务不可达 | Feign 调用超时/连接拒绝 | 检查注册中心服务注册，不 mock 绕过 |

新踩到的坑记录到项目规范（排查类规范），积累为团队知识。

## 交付前角色

- 本环节产出的测试通过记录 = 验收标准「可重复验证证据」的主要来源；review 环节据此核对证据真实性。
- 测试全部通过 ≠ 任务完成：仍需 winin-sop-review 做交付前审查（范围/影响面/质量）。
